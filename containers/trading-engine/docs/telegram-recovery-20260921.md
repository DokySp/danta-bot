# Telegram 기록 조사와 복구 작업

## Fact: 조사 범위와 발견한 문제

NAS의 `telegram-gateway/memory/telegram-conversations` 2026-06-18~09-21, 83개 날짜·3,393개 기록을 조사했다. 아래 당일 집계는 09-21 10:08 KST 스냅샷 기준이며 이후 수신분을 포함하지 않는다. 활성 NAS SQLite는 직접 열지 않고 로컬 복사본으로 확인했다.

- 당일 260개 기록 중 수신 21개, 송신 239개였다. 텍스트 237개·문서 2개였고, JSON 형태 215개·접수 문구 10개가 있었다.
- 보호 감시 장애 75회·복구 74회·계좌 미완료 48회로 운영 경고 197개가 반복됐다.
- 03:11·03:16 로그인 필요 → 03:22 준비 완료 뒤에도 03:23·03:31 일반 대화는 약 0.5초 이내 `PROCESS_FAILED`였다. 이벤트 파일과 사용량이 비어 있고 stderr 원인이 버려졌다.
- 09:20 투자 검토는 계좌 미완료로 모델을 호출하지 않았다. 반면 원장에는 보호 매도 5건이 체결로 기록돼 있었다. 기존 일일 보고서는 검토 결과만 읽어 이 5건을 누락했다.
- `InterfaceError`로 서비스 worker가 반복 종료됐지만 예외 종류 외 위치가 없었다. 공유 SQLite 연결의 일부 읽기는 잠금을 사용하지 않았다.
- 공시 원문 캐시가 약 285MB로 커졌고 계좌 관측 저장도 전체 캐시를 다시 직렬화·저장했다.
- 일반 대화는 계좌 자료를 받지 못했고, 첨부는 다른 컨테이너의 경로만 전달됐다. `/stop`은 대화 취소가 아니라 투자 일시정지였다.
- gateway에는 작성 중/draft API가 있었지만 엔진이 호출하지 않았다. 명령 메뉴는 18개였고 실제 구독 잔여 한도 조회가 빠졌다.

과거 기록에는 6월 감축 의도와 목표 수량의 불일치, 보유 유지 판단의 목표 0 처리, 7월 이전 위험 감축 표시 잔존·거래 타임라인 해석 혼선·재시작 후 스케줄 누락·첨부 경로 문제, 뉴스 수집 실패 70건, 직접 파이프라인 실패 42건, 일반 오류 13건, 사용 한도 오류 5건, 문서 전송 실패 4건, 9월 스키마 오류가 있었다. 삭제된 구 엔진의 현상이므로 현재 결함과 동일하다고 간주하지 않았다. 현재 주문 권한·목표 수량·중복 방지·보호 우선·기한 지난 심사 재실행 금지 계약은 보존했다.

## Fact: 확인한 결과와 한계

- 개발 PC의 기존 ChatGPT 인증 볼륨으로 실제 `gpt-5.6-sol`, `xhigh` 연결에 성공했다. 단일 시도, 입력 6,589·출력 18토큰의 합성 연결 점검이며 브로커 호출·Telegram 발송은 0회였다. 실제 구독 한도 조회도 성공했다. NAS 인증 확인과 동일한 증거는 아니다.
- 같은 CLI 이미지의 합성 인증으로 API 키 로그인 확인 성공 뒤 ChatGPT 강제 방식에서 0.078초 만에 종료되는 사례를 재현했다. NAS의 두 실패가 이 원인이었는지는 확정되지 않았다.
- 기존 KIS 토큰으로 조회만 수행한 시점에는 주문 612건·7페이지, 잔고 8건, 취소 가능 0건, 예약 조회 6건 모두 COMPLETE였다. POST·토큰 갱신·주문은 하지 않았다. 과거 계좌 장애의 정확한 API 원인은 기존 기록에 남아 있지 않았다.
- 데스크톱과 390px 모바일 합성 HTML을 화면으로 확인했다. 실제 계좌 자료를 미리보기 서버에 게시하지 않았다.
- 읽기 전용 독립 검토에서 확인한 한글 첨부 JSON 크기, 진행 draft ID 범위, 대기 첨부 초과 후 복구, 미확인 수수료의 0원 표시를 수정했다. NAS 원장의 당일 보호 체결 5건도 비용 미확인 상태였다. 예전 0원 기록은 확인 근거가 없어 미확인으로 표시하고, 새 체결 기록에는 비용 확인 여부를 남긴다.
- 입력 첨부는 UTF-8 텍스트 최대 5개·합계 32KiB다. PDF·이미지·바이너리 해석은 지원하지 않으며 명시적으로 안내한다. 실제 송수신·장중 보호·NAS 프로세스 상태는 별도 운영 검증이 필요하다.
- NAS SSH 22번 포트 연결은 거절됐다. 배포 스크립트의 이미지 푸시와 설정 파일 복사를 NAS 컨테이너 재생성·새 버전 실행 확인으로 표시하지 않는다.

## Guess: 아직 확정되지 않은 원인

과거 `PROCESS_FAILED`는 인증 방식 불일치와 실행 환경 문제를 포함한 후보가 남아 있다. 계좌 조회의 반복 실패도 현재는 재현되지 않았다. shared SQLite 경합과 큰 캐시의 반복 저장은 확인된 결함이지만, 누락된 traceback 때문에 과거 모든 `InterfaceError`의 원인이라고 단정하지 않는다. 새 버전의 안전한 진단 기록과 운영 관측으로 구분해야 한다.

## Fact: NAS AI 실행 실패 후속 복구

- NAS 관리 화면의 실행 중인 엔진에서 확인했다. `/app/auth/auth.json`과 `config.toml`은 UID 10001이지만 Codex DB·캐시·세션·잠금 파일 대부분은 root 소유였다.
- 같은 컨테이너에서 UID 10001과 실제 제한된 실행 명령으로 주문과 분리한 연결 점검을 수행했다. 로그인 파일을 읽은 뒤 `failed to initialize in-process app-server client: Permission denied`로 종료했다. 종료 코드 1, 응답 이벤트·사용량·최종 응답 모두 없었다.
- 시작 시 전용 Codex 저장소의 기존 파일·하위 디렉터리 소유권을 UID 10001로 복구한다. 파일 내용과 모드는 보존하고 심볼릭 링크는 따라가지 않으며, 외부 파일을 바꿀 수 있는 하드 링크는 거절한다. 거래 원장은 순회하지 않는다.
- NAS 터미널에서도 로그인은 `python -m danta.container_init codex ...`로 실행하도록 배포 절차에 명시했다. root CLI가 다시 런타임 파일을 생성하는 일을 예방한다.
- NAS에 같은 소유권 복구 함수를 적용한 뒤 UID 10001의 실제 `gpt-5.6-sol` 연결 점검이 성공했다. 종료 코드 0, `connection_ok` 최종 응답, 입력 6,410·출력 16토큰, stderr 없음이었다. 이 짧은 진단의 effort만 low였으며 운영 xhigh 설정은 바꾸지 않았다. 주문·브로커·Telegram 전송은 호출하지 않았다.
- 13:32 KST 동일 NAS 인증으로 실제 사용량 조회도 `CURRENT`와 한도 응답을 반환했다. 앞선 `/usage` 시간 초과 경로가 복구됐음을 확인했다.
- 전체 회귀 337개와 실제 Docker UID 전환 후 쓰기 검사를 통과했다. 독립 읽기 전용 검토에서도 추가 결함이 발견되지 않았다.
