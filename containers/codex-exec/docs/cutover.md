# 별도 승인된 운영 전환

현재 구현은 운영 전환을 수행하지 않았다. `STRATEGY_UNPROVEN`,
`EXTERNAL_INTEGRATION_UNVERIFIED`, `LIVE_NOT_AUTHORIZED`다. 이미지 빌드, 이미지 push,
서버 파일 동기화, 기존 프로세스 정지, 새 컨테이너 시작, 주문 권한 활성화, 실제 체결 검증은
각각 별도의 사실과 승인 범위로 기록한다.

## 전환 전에 사람이 확정할 내용

- 실제 전략 자금·계좌·현금과 종목별 관리 수량/외부 수량 귀속.
- 밤·주말 보유, 허용 손실·주문 종류, 앱 장애 시 native stop 부재 수용 여부.
- 기존 보유와 미체결 주문의 유지·취소·인수 방침.
- 실제 모델/effort·인증·운영비 배분, KIS/DART/시세 사용과 호출 성능.
- 향후 paper 평가와 실거래 승격 검토 조건, 운영 전환 대상 서버와 절차.

연구 기본값을 live_mandate로 자동 복사하지 않는다. 미정 정책을 0·무제한·묵시적 승인으로
취급하지 않는다. 필요한 선택이 미정이면 `WAITING_FOR_HUMAN`으로 질문하고 중단한다.

## 승인 후의 순서

1. 승인된 방식으로 기존 writer의 신규 주문 생성을 중지한다. 코드 삭제가 프로세스 정지라는
   뜻은 아니다. 별도 gateway/KIS MCP/인증 volume을 삭제하지 않는다.
2. 브로커의 잔고·활성 주문·최근 체결·현금과 전략 귀속을 대사한다. UNKNOWN을 새 주문으로
   대체하지 않는다. 수동/해외 자산을 전략 bootstrap에 합산하지 않는다.
3. 기존 운영 상태의 안전한 백업과 복원 검증을 완료한다. 새 DB의 초기 관리 수량·현금·평가는
   승인된 인수 시점에서 시작한다. DB 파일을 지우고 정상 상태를 만들지 않는다.
4. 로컬 저장소·공유 writer lock·read-only secret/approval mount·허용된 네트워크를 검증한다.
   같은 계좌를 다른 alias/컨테이너로 열어도 두 번째 writer가 거절되어야 한다.
5. 공식 calendar/ticks/costs·환경별 API 권한·pagination·시세 freshness·보호/대사 성능·복구를
   실제 허용된 환경에서 검증하고 비식별화 증적을 남긴다. 연결 확인용 실제 주문은 만들지 않는다.
6. 고정 code/config/strategy/prompt/model hash를 명시한 trusted approval과 완전한
   live_mandate를 운영자가 제공한다. `activate --approval ... --expected-config ...`는 이
   기록·현재 계좌·운영 증거와 일치할 때만 실행한다. 코드 테스트 합격은 이 승인을 대신하지 않는다.
7. 승인된 새 프로세스의 대사·보호 상태를 확인한 뒤 신규 위험 확대를 허용한다. 배포와 실제
   체결 확인을 분리해 기록하고, 문제가 있으면 신규 확대를 정지한 채 승인된 보호·대사를 유지한다.

롤백도 사용자 방침에 따른다. 새 미체결/부분체결/보유가 있는 상태에서 이전 DB를 덮어쓰거나
두 writer를 동시에 구동하지 않는다. `/pause`는 신규 재량 확대 중단이며 주문 일괄 취소·
전량매도·보호 종료를 뜻하지 않는다. 낙폭·UNKNOWN·권한 만료의 재개는 새 trusted 판단을
필요로 한다. 관측하지 않은 향후 60+20세션 성과를 전환 완료 근거로 만들지 않는다.
